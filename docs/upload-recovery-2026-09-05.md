# 업로드 재개 정합성 변경 (2026-09-05)

## 적용 순서

1. 백엔드 저장소의 `db_migration_upload_receipt.sql`을 대상 PostgreSQL에 적용한다.
2. `/board/saveUpload`가 포함된 백엔드를 배포한다. 기존 `/board/saveAll`은 구버전 앱용으로 유지한다.
3. 테스트 계정으로 새 API 응답과 동일 Idempotency-Key 재요청 시 게시물 1건 생성을 확인한다.
4. 아래 실기기 점검을 마친 뒤 새 앱을 배포한다.

이 작업에서는 운영 DB 변경, 서버/앱 배포, 실제 게시물 생성은 하지 않았다.
앱을 먼저 배포하면 파일 전송 후 게시 API가 실패하여 큐에 남는다. 구버전 API로 자동 폴백하지 않는다.
서버 롤백 시에도 완료 영수증 테이블/행을 지우지 않는다. 새 앱의 게시 기능은 서버 복구 전까지 대기할 수 있다.

## 변경 내용

- 원본 복사와 작업 기록 저장 후에만 전송한다. 일부 파일 복사 실패 시 일부만 게시하지 않는다.
- 파일별 일회용 URL, 미디어 ID, 네이티브 작업 ID, 준비 경로, 성공 결과를 `checkpoint`에 기록한다.
- 네이티브 등록 전에 계획을 저장하며, 재실행 시 같은 작업 ID의 상태를 조회한다.
- 완료된 파일은 재전송하지 않는다. 실패/작업 부재가 확인된 파일에만 새 티켓과 새 작업 ID를 만든다.
- 상태 조회 실패/장기 실행/등록 응답 유실은 성공이나 실패로 단정하지 않는다. 기록을 남기고 재시도를 안내한다.
- 사진 묶음을 한 번에 OS에 등록한다. 새 게시와 재개는 앱 내부에서 직렬 처리한다.
- 영상 압축본과 HEIC 변환본을 큐 폴더에 보관한다. 완료된 전송을 재개할 때 재압축/재변환하지 않는다.
- 게시 본문을 최초 전송 전에 고정한다. `skysnap-{job UUID}`를 Idempotency-Key로 보낸다.
- 서버는 로그인 계정과 키로 영수증을 식별한다. 계정 행 잠금 후 게시 생성과 영수증 기록을 하나의 트랜잭션으로 처리한다.
- 게시 성공을 로컬에 기록한 다음 네이티브 상태/큐 파일을 정리한다.

## 검증 범위와 한계

- 실행 결과: `flutter test --no-pub` 74개 통과, 백엔드 `./gradlew test bootJar --console=plain` 59개 통과 및 JAR 생성. Android debug APK / iOS debug unsigned 빌드 성공. 변경 Dart 파일 analyze error/warning 0(기존 info 5개).
- Flutter 단위 테스트: 네이티브 상태를 모사하되, 큐 파일 복사/저장/재로드는 실제 임시 디렉터리에서 실행한다.
- 서버 단위 테스트: 응답 유실 재시도, 본문 변경 거부, 계정별 키 격리, 실패 시 영수증 미생성.
- H2 통합 테스트: 실제 JPA 계정 행 잠금, 동시 요청 1건 생성, 예외/영수증 기록 실패 시 트랜잭션 롤백. 게시 서비스의 외부 알림 등은 모사한다. 운영 PostgreSQL/전체 게시 서비스 통합 검증과는 다르다.
- 이전 버전 큐에는 티켓이 없으므로 기존 OS 작업의 종료를 확인한 뒤 새 전송으로 이관한다. 이전에 완료된 파일/게시물의 식별자가 없으면 완전한 중복 제거는 보장할 수 없다.
- multipart 전송이다. 바이트 오프셋 기반 tus 재개를 새로 구현한 것은 아니다.
- OS가 전송을 끝내도 티켓 발급/최종 게시는 Dart 실행이 필요하다. iOS 사용자 강제 종료, Android 설정의 강제 종료 후 자동 완료를 보장하지 않는다.
- 현재는 운영 배포 전 코드 변경이다. 모모앨범과의 성능 동등성이나 실기기 업로드 속도 향상을 실측한 결과가 아니다.

## 실기기 출시 게이트 (아직 미실행)

- Android/iOS 각각 사진 1장/여러 장, 대문자 확장자 HEIC, 압축 대상 영상으로 정상 게시 확인.
- OS 등록 직전, 전송 중, 일부 사진 성공 후, 게시 응답 직전 각각 앱 종료/재실행. 원래 미디어 ID 유지 및 게시물 1건 확인.
- Wi-Fi ↔ 이동통신 전환, 오프라인 후 복귀, 상태 조회 채널 실패, 네이티브 등록 응답 유실 확인.
- 서버 저장 성공 후 응답만 유실시켜 동일 키 재시도. PostgreSQL에서 게시물과 영수증이 각각 1건인지 확인.
- 계정 변경 시 이전 계정의 큐가 새 계정으로 게시되지 않는지 확인.
- 저장 공간 부족, 보관 파일 일부 부재 시 부분 게시 없이 실패 안내/큐 보존 확인.
- 구버전에서 실패해 남은 큐의 이관과 서버 선배포/앱 후배포 조합 확인.
